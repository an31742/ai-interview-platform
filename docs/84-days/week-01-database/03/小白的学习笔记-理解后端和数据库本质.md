## 二、B：后端到底是怎么工作的？

### 一个故事讲通全部

```
你打开网页（浏览器）               = 你走进餐厅
页面上的"注册"按钮                  = 你跟服务员说"我想登记会员"
这个请求发到 POST /api/auth/register = 服务员对着厨房喊
后端（Next.js）接到请求             = 厨师听到喊声
后端去查/写数据库                  = 厨师打开冰箱拿食材
后端返回结果给前端                  = 服务员把菜端到你面前
你的页面显示"注册成功"             = 你吃到了菜
```

### 后端本质

```
后端 = 运行在服务器上的一段程序
      永远在等着前端来"敲门"
      前端敲门说"我要注册" → 后端处理 → 返回结果

你电脑上现在跑着的：
  npm run dev → 启动了 Next.js 开发服务器
              这个服务器就是一个"后端程序"
              它监听 localhost:3000 这个地址
              谁来敲门它都处理
```

### 注册功能拆开看

用户点"注册"按钮后发生了什么：

```
第 1 步：浏览器发请求
  → POST http://localhost:3000/api/auth/register
  → 带了数据：{ email, password, name }

第 2 步：Next.js 路由匹配
  → 找到 src/app/api/auth/register/route.ts 这个文件来处理

第 3 步：route.ts 执行（这就是"后端"）
  → 拿出 email, password, name
  → 校验格式
  → 查邮箱是否已注册
  → 加密密码
  → 存用户（目前存 JSON 文件）
  → 返回 { user, token }

第 4 步：浏览器收到响应
  → 页面显示"注册成功"或"邮箱已注册"
```

## 三、C：前端和后端是怎么连起来的？

### 最核心的理解

```
前端（浏览器里的页面）               后端（Next.js 服务器）
┌─────────────────────┐      ┌──────────────────────┐
│                     │      │                      │
│ fetch("/api/auth/   │ ──→  │ register/route.ts    │
│ register", {...})   │      │                      │
│                     │      │  1. 校验参数          │
│                     │ ←──  │  2. 查是否重复        │
│ if (res.ok) {       │      │  3. 哈希密码          │
│   注册成功          │      │  4. 存数据库          │
│ } else {            │      │  5. 返回结果          │
│   显示错误          │      │                      │
│ }                   │      │                      │
└─────────────────────┘      └──────────────────────┘
      ↑ 唯一的交流方式：发请求 ↔ 等响应
```

### 三个关键理解

**理解 1：前端和后端是"两个完全独立的程序"**

```
前端 = 跑在浏览器里的代码（React 页面）
后端 = 跑在服务器上的代码（Next.js API routes）

它们唯一的交流方式就是"发请求 ↔ 等响应"

就像打电话点外卖：
  你（前端）："我要一份宫保鸡丁"
  餐厅（后端）："好的，30分钟送到"
```

**理解 2：前端不能直接碰数据库**

```
❌ 前端不能：prisma.user.create({...})
   → 浏览器没有 Prisma，也连不上数据库

✅ 前端只能：fetch("/api/auth/register", {...})
   → 发请求给后端，让后端处理数据库
```

**理解 3：API 就是"前后端约定好的暗号"**

```
API = Application Programming Interface

注册这个 API 的约定：
  前端发：POST /api/auth/register
         { email, password, name }
  后端返（成功）：{ user, token }
  后端返（失败）：{ error: "邮箱已注册" }

双方都遵守这个约定，就能愉快合作
```

### 之前理解错的地方

```
❌ 以前以为：前端 → 调用 → 后端的数据库 → 展示
✅ 实际情况：前端 → 调用 → 后端（后端查数据库）→ 返回给前端 → 展示

前端从来不直接碰数据库，它只跟后端说话。
后端去数据库查，取回来，交给前端。
```

### 一句话总结

```
后端 = 中间人
  前端说"我要 xxx" → 后端去数据库查 → 后端取回来 → 后端交给前端
```

## 四、A：数据库到底是什么鬼？

### 本质理解

```
数据库 = 一个专门存数据的大仓库 + 一个超级智能的管家
```

### JSON 文件 vs 数据库（亲身对比）

```
JSON 文件（以前的方式）：
  .rag-data/users.json
  → 就是文本文件，记事本也能打开
  → 查数据：整个文件读到内存，一个个遍历
  → 就像把整个仓库的货搬出来，一件一件翻

SQLite 数据库（现在的方式）：
  dev.db
  → 也是文件，但记事本打开是乱码
  → 查数据：跟管家说一声就行
  → 管家找到，只拿那一件出来
```

### 对比表

| 对比 | JSON 文件 | 数据库（SQLite） |
|------|----------|----------------|
| 本质 | 一个文本文件 | 一个带"管家"的仓库 |
| 查数据 | 全部读到内存，遍历 | 跟管家说一声，管家去找 |
| 速度 | 100 个还行，1 万就慢 | 100 万也是毫秒级 |
| 多人同时用 | 可能冲突 | 自动处理并发 |
| 数据完整性 | 写到一半断电→文件坏 | 有保护机制 |
| 怎么操作 | JS 代码读写文件 | Prisma 翻译成 SQL 命令 |

### SQLite vs PostgreSQL vs MySQL

```
都是数据库，就像可口可乐、百事可乐、非常可乐

SQLite     = 一瓶小可乐，不用开瓶器（不用安装）
             数据存在一个文件里，适合学习/小项目/手机 App

PostgreSQL = 一大桶可乐，要装龙头（要安装服务器）
             功能更强大，适合正式项目/多人使用

MySQL      = 另一品牌的大桶可乐，也很流行

你现在用 SQLite 学习完美。
以后把 provider 改成 postgresql 就切换了。
Prisma 最大的好处：换数据库像换可乐品牌一样简单。
```

### 一个比喻记住数据库本质

```
没有数据库：
  你开小店，顾客信息写笔记本上
  查"王先生的电话"——翻整本笔记本
  笔记本被水泡了——数据全没了

有数据库：
  雇了一个管家，顾客信息交给管家管
  说"查王先生电话"——几秒就找到
  笔记本被泡了——管家有备份
  两人同时改——管家说"一个一个来"
```
