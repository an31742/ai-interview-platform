## 二、三层架构的完整流程

### 注册一个用户，背后发生了什么

```
你的点击"注册"按钮
    ↓
① Controller（register/route.ts）—— 服务员
    body = await request.json()          ← 解析请求
    user = await userService.register()  ← 调 Service
    return Response.json({ user, token }) ← 返回响应
    ↓

② Service（user.service.ts）—— 厨师
    if (password.length < 6) throw       ← 检查密码长度
    existed = await userRepo.findByEmail() ← 调采购员查
    if (existed) throw                   ← 判断邮箱重复
    salt = await generateSalt()          ← 生成随机盐
    passwordHash = await hashPassword()  ← 加密密码
    user = await userRepo.create()       ← 调采购员存
    return toSafeUser(user)              ← 去掉密码再返回
    ↓

③ Repository（user.repository.ts）—— 采购员
    prisma.user.findUnique({ where: { email } })  ← 查数据库
    prisma.user.create({ data: {...} })            ← 写数据库
    ↓

④ SQLite（dev.db）—— 数据库管家
    User 表真的多了一行数据
```

### 关键理解：每一层只干自己的事

```
Controller：  "来的是什么请求？我要调谁处理？怎么返回？"
             → 不写业务逻辑，不查数据库

Service：     "这个操作合不合法？要做什么处理？"
             → 不做 HTTP 处理，不直接查数据库
             → 只调 Repository，只做判断和转换

Repository：  "怎么查？怎么写？"
             → 不判断业务规则，只执行数据库操作
```

## 三、register 方法逐行讲解

### 第 1 步：检查密码长度

```typescript
if (!password || password.length < 6) {
  throw new BusinessError("密码至少 6 位");
}
```

为什么放 Service 不放 Controller？
- 这是"业务规则"。以后有 App、小程序、网页多个前端，每个前端都要写一遍密码检查？
- 写在 Service 里，所有入口共享同一个规则。

### 第 2 步：查邮箱是否已注册

```typescript
const existed = await userRepository.findByEmail(email);
if (existed) {
  throw new BusinessError("该邮箱已注册");
}
```

关键：
- Service **调用** Repository 去查
- Service **自己判断**结果
- Repository（采购员）："仓库里有这个货" ← 只负责查
- Service（厨师）："已经被别人订了" ← 负责判断

### 第 3 步：哈希密码

```typescript
const salt = await generateSalt();
const passwordHash = await hashPassword(password, salt);
```

用户输入 "123456" → 加上随机 salt 加密 → 变成乱码存进数据库
**密码原文永远不会存进数据库。**

### 第 4 步：创建用户

```typescript
const user = await userRepository.create({
  email: email.toLowerCase().trim(),  // 统一转小写
  name: name.trim(),
  passwordHash,
  salt,
});
```

Service 喊 Repository 去存，自己去调用 Prisma。

### 第 5 步：返回安全版本

```typescript
return userRepository.toSafeUser(user);
```

去掉 passwordHash 和 salt，密码永远不返回到前端。

## 四、BusinessError 是什么？

```typescript
export class BusinessError extends Error {
  constructor(message: string) {
    super(message);
    this.name = "BusinessError";
  }
}
```

- **普通 Error**（系统错误）：数据库连不上、服务器崩溃 → 返回 500
- **BusinessError**（业务错误）：密码太短、邮箱已注册 → 返回具体错误信息

Controller 这样区分：
```typescript
if (err instanceof BusinessError) {
  return Response.json({ error: err.message }, { status: 409 });
}
// 其他错误 → 返回"服务器内部错误"
```

## 五、其他语言也是这样的吗？

**是！思路一模一样，只换语法。**

| 概念 | Node/TypeScript | Java | Python | Go |
|------|----------------|------|--------|-----|
| Service | `const service = {...}` | `class UserService` | `class UserService:` | `type UserService struct` |
| 调 Repository | `userRepo.findByEmail()` | `userRepo.findByEmail()` | `self.repo.find_by_email()` | `s.repo.FindByEmail()` |
| 抛业务错误 | `throw new BusinessError()` | `throw new BusinessException()` | `raise BusinessError()` | `return nil, errors.New()` |
| 校验 | `if(len<6)` | `if(len()<6)` | `if len < 6` | `if len < 6` |

**核心思想全部一样：**
1. Service 负责判断规则
2. Repository 负责查数据库
3. Service 不直接查数据库
4. Repository 不做业务判断

**你现在学的不是 Node，是后端的通用思维方式。**
