## 📌 开胃菜：一个核心比喻

在开始之前，先把这个比喻刻在脑子里：

```
数据库                =  你的衣柜
数据表（Table）        =  衣柜里的抽屉
一行记录（Row）        =  抽屉里的一件衣服
一个字段（Column/Field）=  这件衣服的一个属性（颜色、尺码、品牌）
主键（Primary Key）    =  每件衣服上的"标签牌"——独一无二
外键（Foreign Key）    =  标签牌上写的"这袖子配哪件外套"
索引（Index）          =  抽屉外面的标签"长袖/短袖/外套"
```

**接下来所有内容，都回到这个比喻上来理解。**

## 一、为什么需要"设计"？不能直接写代码吗？

### 核心概念：先画图纸再施工

```
❌ 错误做法：
  写代码 → 发现需要存数据 → 临时建个表 → 需求变了 → 再改表
  → 像一个衣柜做好了，发现装不下，拆了重新做

✅ 正确做法：
  想清楚有哪些数据、它们之间什么关系 → 设计表结构 → 写代码
  → 像先量尺寸、画图纸、再打衣柜
```

### 为什么不能边写边改？

因为你用的是**数据库**，不是 Excel：

| | Excel | 数据库 |
|--|-------|--------|
| 加一列 | 右键插入，2 秒 | 要跑 Migration（像 Git 提交） |
| 改列名 | 双击改，1 秒 | 不能直接改，要写命令 |
| 删一列 | 右键删除，1 秒 | 可能把关联数据也删了 |
| 关联数据 | 靠人眼匹配 | 有约束，不能乱来 |

**结论：数据库设计错了，改起来比 Excel 痛苦 10 倍。所以先想清楚。**

## 二、数据库里最基本的单位：一张"表"

### 表是什么？

一张表 = 一类东西的集合。

```
User 表    → 存所有"用户"的信息
Resume 表  → 存所有"简历"的信息
JD 表      → 存所有"职位描述"的信息
```

**每张表只管它自己的那一类东西。**

> 你的 AI 面试训练平台，有哪些"东西"需要存？
>
> （提示：用户、简历、面试记录、面试题目、面试评价……别急着回答，想想还有没有漏的）

## 三、表和表之间的关系（最重要的一节）

### 为什么关系最重要？

因为数据库不是 Excel——**表之间是相互连接的**。

```
一个用户 → 可以有多份简历
一个用户 → 可以参加多次面试
一份简历 → 对应多个面试题目
```

如果不理解"关系"，你就不知道怎么把表连起来。把表连起来，才是数据库的真正用途。

### 最常见的三种关系

#### ① 一对一（1:1）

```
一个人 → 一本护照

关系：一个人只有一本护照，一本护照只对应一个人
```

#### ② 一对多（1:N）—— ⭐你最关心的

```
一个用户 → 多份简历

关系：一个人可以投递多份简历
       但每份简历只属于一个人

这是你项目中 User 和 Resume 的关系。
```

#### ③ 多对多（N:M）

```
一个学生 → 多门课程
一门课程 → 多个学生

关系：学生可以选多门课，一门课可以被多个学生选
      需要第三张表来记录"谁选了哪门课"
```

### 🤔 问自己一个问题

> 你的项目中，User 和 Resume 之间是一对多，对吧？
> 那为什么不是"一对一"？（即每个用户只能有一份简历）
> 为什么不是"多对多"？（即一份简历可以属于多个用户）
>
> **想清楚了这一点，你就理解了为什么你的 Resume 表需要有一个 userId。**

## 四、关系在数据库里怎么表示？

### 核心概念：外键（Foreign Key）

外键 = 在"多的那一方"加一个字段，指向"一的那一方"。

```
User 表（一的那方）
┌─────────┬────────┬────────┐
│ id      │ email  │ name   │
├─────────┼────────┼────────┤
│ user001 │ a@...  │ 张三   │
└─────────┴────────┴────────┘
                              ↑
                              │
Resume 表（多的那方）           │
┌─────────┬──────────┬────────┐
│ id      │ userId ──┘        │
├─────────┤         │  fileName │
│ res001  │ user001  │ 我的简历  │
│ res002  │ user001  │ 英文简历  │
│ res003  │ user002  │ 张三的简历 │
└─────────┴──────────┴────────┘
```

**关键理解：**
- Resume 表里的 `userId` 不存"用户的名字"，存的是用户的 `id`
- 就像快递上的收件人地址，不是写"住在一栋漂亮房子里的人"，而是写"XX 路 XX 号"
- 因为地址（id）是唯一的，描述（名字）不是唯一的

### 🤔 问自己一个问题

> 如果 Resume 表没有 `userId` 字段，你怎么知道一份简历属于哪个用户？
>
> 如果两个用户有同名的简历，你怎么区分"谁是谁的"？

## 五、怎么设计一张表的字段？

### 每个字段都要回答 3 个问题

设计字段不是"想存什么是存什么"，是问自己 3 个问题：

#### 问题 1：这个信息重不重要？

```
级别 1（必须有）    → 这个字段不能为空          → String（不带问号）
级别 2（可能有）    → 这个字段可以为空          → String?（带问号）
级别 3（以后可能）  → 现在不加，以后再说        → 先不写
```

#### 问题 2：这个信息怎么识别？

```
唯一标识符（像身份证号）→ @unique  → 比如 email
普通信息（像身高体重）   → 不加约束 → 比如 name
```

#### 问题 3：这个信息谁生成？

```
用户填的     → 用户注册时输入     → 比如 email, name, password
系统生成的   → 自动生成           → 比如 id, createdAt, updatedAt
程序计算的   → 由其他数据算出     → 比如 "简历得分"从面试记录算出来
```

### 🤔 用这三问来想想 User 表的字段

> 先别管答案，用上面的框架想一遍：
>
> | 字段 | 重要程度？ | 唯一吗？ | 谁生成？ |
> |------|-----------|---------|---------|
> | id | 必须有 | 必须唯一 | 系统 |
> | email | ? | ? | ? |
> | name | ? | ? | ? |
> | password | ? | ? | ? |
>
> 把空格填了，你就在设计数据库了。

## 六、id 是什么？为什么要选"类型"？

### id 是什么

id = 每行记录的身份证号。

每一行数据都要有一个独特的 id，就像每个人都有一个身份证号。

### 不同的 id 类型

#### ① 自增（Auto-increment）：1, 2, 3, 4 ...

```
优点：数字小，看着舒服，性能好
缺点：
  - 暴露信息：第 100 个注册的人 id=100，别人知道你至少 100 个用户
  - 合并麻烦：两个数据库合并时，id 会冲突（都有 id=1）
  - 不安全：别人可以猜 id，比如 /user/3 试试能不能看
```

#### ② UUID 或 CUID：像乱码一样

```
例子：ckl8f3h2d0000y3i5f6k7g8h9

优点：
  - 全世界唯一：两个系统各自生成，永远不会冲突
  - 不暴露信息：看不出你总共有多少用户
  - 安全：别人猜不到别人的 id
缺点：
  - 字符串比较慢一点（但现在的数据库完全感受不到差别）
  - 调试时复制粘贴比较长
```

### 🤔 问自己一个问题

> 你的项目未来会不会：
> ① 部署到多个服务器？
> ② 数据库拆分？
> ③ 合并多个数据库的数据？
>
> 如果"有一个会"，自增 id 就会遇到问题。
>
> 另外想一想：如果你的网站显示用户 id = 1，用户会怎么想？

## 七、密码存在哪？怎么存？

### 先想清楚两个概念

```
密码 ≠ passwordHash

密码（password）         = 你输入的 "abc123"
密码哈希（passwordHash） = 把 "abc123" 通过算法变成一堆乱码
```

**数据库里永远不存密码原文。** 只存密码的哈希值。

```
你注册时输入 "abc123"
  → 系统把它变成哈希：$2b$10$rO0aKbF8...
  → 存入数据库的 passwordHash 字段

你登录时输入 "abc123"
  → 系统也变成哈希：$2b$10$rO0aKbF8...
  → 和数据库里的 passwordHash 比对
  → 一样 → 登录成功
```

这样即使数据库泄露，别人也拿不到你的密码。

### salt 又是什么？

```
salt = 给密码加点"调料"

不加 salt：
  两个人都用 "abc123" → 哈希值一模一样
  黑客一看就知道他们密码相同

加 salt：
  给每个人各生成一个随机字符串（salt）
  "abc123" + saltA → 不同的哈希值
  "abc123" + saltB → 又不同的哈希值
  即使密码相同，存出来的 hash 也不同
```

### 关键问题

> **passwordHash 和 salt 放 User 表本身？还是单独建一张 Password 表？**
>
> 想一想：
> - 一个用户有几个密码？（一个）
> - 你什么时候需要用到 passwordHash？（登录时）
> - 登录时你需要同时知道"这是哪个用户"和"他的密码对不对"
>
> 放到不同表意味着：登录时要查两次数据库。
> 放到同一张表：一次就查到。
>
> **那么问题来了：分开还是合并？哪种更合理？**

## 八、时间戳：谁负责记时间？

### createdAt 和 updatedAt

```
createdAt = 这条记录什么时候创建的
updatedAt = 这条记录最后一次什么时候修改的
```

### 两种做法

#### 做法 A：程序员手动维护

```javascript
// 每次创建用户时
user.createdAt = new Date()
// 每次修改用户时
user.updatedAt = new Date()
```

问题：如果你忘了写呢？如果不同的人写法不一致呢？

#### 做法 B：数据库自动维护

```prisma
createdAt DateTime @default(now())
// 创建时自动记录当前时间，不需要代码管

updatedAt DateTime @updatedAt
// 每次修改时自动更新时间，也不需要代码管
```

### 🤔 问自己

> 如果让你选，你会选 A 还是 B？为什么？
>
> 假如你是一个团队的管理者，你希望团队成员"自觉记时间"还是"系统自动记时间"？

## 九、JSON 字段 vs 单独表

### 什么时候用 JSON？

JSON = 在数据库字段里塞一个"小文档"。

```
Resume 表
┌─────────┬──────────┬──────────────────────────────────────┐
│ id      │ userId   │ parsed（JSON 类型）                    │
├─────────┼──────────┼──────────────────────────────────────┤
│ res001  │ user001  │ { "name": "张三", "phone": "138..." } │
└─────────┴──────────┴──────────────────────────────────────┘
```

#### JSON 适合的场景

```
✅ 数据结构不固定：
   每份简历解析出来的字段可能不同
   有的简历有"项目经历"，有的没有
   有的简历有" GitHub 链接"，有的没有
   → JSON 可以灵活装不同结构

✅ 数据是一次性使用的：
   你取出 parsed 字段，直接在页面展示
   不会在数据库里搜索"所有 GitHub 链接以 github.com 开头的简历"
   → JSON 存进去取出来，不查里面

✅ 数据是"有归属"的：
   一份简历的解析结果只属于这份简历
   不会被别的表引用
```

### 什么时候用单独表？

```
❌ JSON 不适合的场景：
   你想搜索"所有简历中，会 React 的用户"
   → JSON 里搜关键词很慢
   → 需要拆成技能表

❌ JSON 不适合的场景：
   parsed 里的数据要被多个表引用
   比如"毕业学校"也要用在用户资料表里
   → 需要拆成学校表
```

### 🤔 问自己

> 你的简历解析结果（parsed）和 AI 分析结果（analysis）：
>
> ① 你以后会搜索"所有简历中技能包含 React 的人"吗？
> ② 这些数据除了展示，会不会被其他地方引用？
> ③ 每份简历的解析结果结构一样吗？
>
> 如果 ①和②是"不会"、③是"不一样"，那 JSON 合适还是单独表合适？

## 十、索引是什么？什么时候加？

### 索引 = 书的目录

```
没有目录（索引）：
  你要找"React"这个词 → 从第 1 页翻到第 300 页
  → 慢，但如果你只翻 5 次书，无所谓

有目录（索引）：
  目录里找到 "React → 第 178 页" → 直接翻到 178 页
  → 快，但目录需要额外占 2 页纸
```

### 不要每本书都加目录

```
索引不是越多越好：

✅ 适合加索引的字段：
   - 经常用来搜索的（按 email 查用户）
   - 经常用来排序的（按创建时间排序）
   - 用来做关联的（userId，用来连接 User 和 Resume）

❌ 不需要加索引的字段：
   - 很少用来搜索的（比如简历的文件名）
   - 值只有几个的（比如 status 只有 "成功"/"失败"）
   - 数据量很小的（几十条数据，翻书比查目录还快）
```

### 🤔 问自己

> 你的项目中，哪些字段会经常用来"查找"？
>
> 比如：登录时要查 email 来找用户 → email 要不要索引？
> 比如：查看某个用户的所有简历 → userId 要不要索引？
> 比如：按创建时间倒序排列 → createdAt 要不要索引？

## 十一、把这些串起来：一张表就是一个"责任范围"

### 现在我们把所有概念合在一起看

```
User 表的"责任"是：管好"用户"的一切
  ✓ 用户是谁（id, email, name）
  ✓ 用户怎么登录（passwordHash）
  ✓ 用户什么时候来的（createdAt, updatedAt）
  ✗ 用户的简历不归 User 表管（那是 Resume 表的事）

Resume 表的"责任"是：管好"简历"的一切
  ✓ 简历属于谁（userId → 指向 User 表）
  ✓ 简历长什么样（fileName, parsed）
  ✓ 简历分析的怎么样（analysis）
  ✓ 简历处理到什么阶段了（status）
  ✗ 用户的名字不归 Resume 表管（那是 User 表的事）
```

### 为什么这样分？

因为**一个字段只应该属于一张表**。

```
如果你的 Resume 表里有：
  userId  → ✅ 对的，因为简历属于用户
  userName → ❌ 错的，用户名是 User 表的事

为什么是错的？
  如果用户改名字了 → 你简历表里的 userName 还是旧的
  你得同时更新 User 表和每一份 Resume 表的 userName
  → 数据不一致，灾难
```

### 核心原则

> **每个信息只在一个地方存一次。其他地方需要它时，用 id 去引用。**

## 十二、用一个场景串通所有概念

现在让我们追踪一个完整的故事，看看你设计的数据表怎么工作：

```
1️⃣ 有一个叫"张三"的人来到你的网站
2️⃣ 张三填了邮箱和密码，点击"注册"
    → User 表新增一行，id = "user_abc123"
    → 系统记下了 createdAt = 当前时间
  
3️⃣ 张三上传了一份简历 "张三的简历.pdf"
    → Resume 表新增一行，id = "res_xyz789"
    → userId = "user_abc123"（指向张三）
    → fileName = "张三的简历.pdf"
    → status = "uploaded"

4️⃣ 系统开始解析简历
    → status 改为 "parsing"
    → 解析完成后，status 改为 "done"
    → parsed 字段填入解析结果（JSON）

5️⃣ AI 分析简历
    → analysis 字段填入分析结果（JSON）

6️⃣ 张三又上传了一份英文简历
    → Resume 表再新增一行，id = "res_111222"
    → userId = "user_abc123"（还是指向张三）
    → fileName = "英文简历.pdf"
    → 看，一个用户有了两份简历（1:N 关系体现出来了！）

7️⃣ 现在要展示"张三的所有简历"
    → 查 Resume 表，WHERE userId = "user_abc123"
    → 用 userId 索引，快速找到两条记录
    → 返回给页面展示
```

**这个流程中，每一张表各司其职，通过 `userId` 联系起来。**

## 写在最后：设计数据库不是"写对答案"

很多新手学数据库会有一种误解：

> "我只要按教程写一个完美的 Schema 就行了"

**不是的。数据库设计没有"标准答案"。**

它更像一个权衡的过程：

```
用自增 id？还是 UUID？
  → 看你的项目是简单博客还是大型系统

密码放用户表？还是单独表？
  → 看你追求简单还是极致安全

JSON 存解析结果？还是拆成 5 张表？
  → 看你的查询需求有多复杂

每一条数据库经验法则，背后都是一个 trade-off（取舍）。
理解 trade-off 是什么，比知道"标准答案"重要 100 倍。
```

### 你现在该做什么？

1. **关上本文**，打开 `prisma/schema.prisma`
2. **用学到的思路**，自己写出 User 和 Resume 的 Model
3. **不要查答案，不要问 AI**，完全凭自己的理解写
4. 写完后，你可以回来，用本文的框架重新检查一遍你的设计：

```
✅ 检查清单：
   □ 每张表只负责一类东西？
   □ Resume 表有 userId 指向 User？
   □ 每个字段想清楚"重要程度"了？
   □ 时间戳交给数据库维护还是自己写代码？
   □ id 类型的选择基于你的实际需求而不是随便选的？
   □ 需要唯一性的字段加了 @unique？
   □ passwordHash 放在该放的位置？
   □ 想清楚 JSON 字段存什么了？
```

**先自己写，再拿给 Claude 验证。这个过程才是真正学会数据库的时刻。**
