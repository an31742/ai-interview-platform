## 二、核心数据流详解

### 2.1 简历上传 → 分析 → 存储

```
┌──────┐   ┌──────┐   ┌────────┐   ┌──────────┐   ┌──────────┐
│用户  │   │浏览器│   │/api/   │   │Resume    │   │ChromaDB  │
│拖拽PDF│   │前端   │   │analyze-│   │Analyzer  │   │(向量库)   │
│      │   │      │   │resume  │   │Agent     │   │          │
└──┬───┘   └──┬───┘   └───┬────┘   └────┬─────┘   └────┬─────┘
   │          │           │             │              │
   │  File     │           │             │              │
   │─────────>│           │             │              │
   │          │  POST     │             │              │
   │          │─────────>│             │              │
   │          │           │  PDF解析     │              │
   │          │           │  pdf-parse  │              │
   │          │           │──────┬─────>│              │
   │          │           │      │      │  文本分段     │
   │          │           │      │      │  TextSplitter│
   │          │           │      │      │──────┬──────>│
   │          │           │      │      │      │       │
   │          │           │      │      │  Embedding   │
   │          │           │      │      │──────┬──────>│
   │          │           │      │      │      │ 向量   │
   │          │           │      │      │      │ 存储   │
   │          │           │      │      │<─────┼───────│
   │          │           │      │      │      │       │
   │          │           │      │ 调用DeepSeek        │
   │          │           │      │────────────────>   │
   │          │           │      │ 结构化JSON返回       │
   │          │           │      │<────────────────    │
   │          │           │ 返回分析结果                │
   │          │           │<──────────┘               │
   │          │  存入      │                           │
   │          │  Zustand   │                           │
   │          │  + persist │                           │
   │          │<──────────│                           │
   │  展示     │           │                           │
   │<─────────│           │                           │
```

**关键设计决策：**

| 环节 | 技术选择 | 为什么 |
|------|---------|--------|
| PDF解析 | pdf-parse（服务端） | PDF解析库需要Node环境，在API route中执行 |
| 文本分段 | RecursiveCharacterTextSplitter | 按段落/句子递归分割，比固定长度更自然 |
| 向量化 | ChromaDB Embeddings | 本地运行，无需额外部署向量数据库服务 |
| 结构化输出 | DeepSeek JSON Mode | 直接从非结构化文本提取结构化数据 |

**面试追问：***"简历文件存在哪里？"*
> 当前用 localStorage（Zustand persist），适合单用户场景。
> V4 计划接入 PostgreSQL，支持多用户和文件管理。

**SSE 流式协议设计：**

```
前端 → 后端 (普通POST)：
{
  "messages": [
    {"role": "ai", "content": "请介绍你自己", "type": "question", "phase": "self-intro"},
    {"role": "user", "content": "我是...", "type": "answer", "phase": "self-intro"}
  ],
  "resumeContext": "7年经验，Vue/React...",
  "jdContext": "要求熟悉...",
  "currentPhase": "self-intro"
}

后端 → 前端 (SSE Stream)：
data: {"type":"chunk","content":"感谢"}
data: {"type":"chunk","content":"你的"}
data: {"type":"chunk","content":"回答。"}
data: {"type":"evaluation","score":7,"comment":"思路清晰，可以深入"}
data: {"type":"phase-change","phase":"project-deep-dive"}
data: {"type":"chunk","content":"我想了解更多..."}
data: {"type":"done","sessionId":"xxx"}
```

**为什么 SSE 而不是 WebSocket？**

```
面试场景：AI在说话（单向流） > 用户在说话（一次性提交）
SSE 天然适合 服务器→客户端的单向流
WebSocket 是全双工，面试场景不需要（用户回答是一次性提交，不是流式的）

对比维度     SSE          WebSocket
协议        HTTP          TCP
方向        服务器→客户端   双向
重连        原生支持       手写心跳
浏览器兼容  所有现代浏览器   所有现代浏览器
适用场景    AI对话流式输出   实时协作/游戏
```

### 3.2 为什么选 Zustand？

| 方案 | 问题 |
|------|------|
| Redux | 样板代码太多，对于这个规模的项目太重 |
| Context | 流式场景每秒更新多次，会导致整个子树重渲染 |
| **Zustand** | ✅ 精确selector订阅，只有变化的部分重渲染 |

```typescript
// ✅ 正确：只有 streamingContent 变化时重渲染
const content = useInterviewStore(s => s.streamingContent)

// ❌ 错误：任何状态变化都重渲染
const store = useInterviewStore()
```

## 四、数据流面试问答

### Q1: 简历上传后，前端怎么拿到分析结果？

**回答：**
> 用户选择PDF文件后，前端 `FormData` 上传到 `/api/interview/analyze-resume`。
> 服务端用 `pdf-parse` 提取文本，传给 ResumeAnalyzer Agent，
> Agent 调用 DeepSeek 提取结构化信息并分析优劣势。
> 分析结果通过 JSON 响应返回，存入 Zustand Store（自动 persist 到 localStorage），
> 前端展示分析报告。整个过程约 3-5 秒。

### Q2: 模拟面试对话怎么保证消息不丢失？

**回答：**
> 每一轮对话由前端管理：
> 1. 用户点击发送 → 立即存入 Zustand（乐观更新）
> 2. SSE 流式接收 AI 回答 → 逐字显示在 UI，流结束后整条消息存入 Store
> 3. 所有消息通过 Zustand persist 写入 localStorage
> 4. 刷新页面 → 从 localStorage 恢复完整对话历史
>
> 不需要额外的消息队列，因为面试场景是低并发的单用户对话。

### Q3: RAG 在系统中的作用是什么？

**回答：**
> RAG 解决 AI 的"长期记忆"问题。
> 简历内容经过 Embedding 存入 ChromaDB 向量库，
> 在模拟面试时，Interviewer Agent 可以从向量库检索相关项目经历来追问。
>
> 没有 RAG，AI 在每轮对话中只能看到当前消息，会"忘记"简历细节。
> 有 RAG，AI 能精确引用简历中的项目来提问，面试更真实。

### Q4: 如果用户网络中断，正在进行的面试会怎样？

**回答：**
> 当前设计是 localStorage 持久化，网络中断时：
> 1. SSE 连接断开 → 前端检测到 error 事件 → 显示"连接中断"提示
> 2. 用户已提交的回答已存在 Store 中，不会丢失
> 3. 重连后用户需要重新提交当前回答（上一轮AI的回答可能不完整）
>
> V3 会加入断线重连机制：SSE 的 lastEventId 实现断点续传。
