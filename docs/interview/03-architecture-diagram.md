## 七、架构面试问答

### Q1: 为什么选 Next.js 而不是纯 React SPA + 独立后端？

> **三个原因：**
> 1. **一体化部署** — 前端页面 + API 路由在同一个项目中，减少部署运维成本
> 2. **SSR/SSG 灵活选择** — 静态页面用 SSG（仪表盘），交互页面用 Client Component（面试对话）
> 3. **流式渲染原生支持** — Next.js 16 的 Streaming 和 SSE 配合得好

### Q2: 为什么用 LangGraph 而不是普通 API 调用管理面试流程？

> 普通 API 调用是"请求-响应"模式，每个请求独立，没有状态。
> 面试需要的是**状态机**：面试官根据用户的回答决定下一步问什么。
> LangGraph 的 StateGraph 维护了面试状态（当前阶段/已问问题/用户评分），
> 通过 `conditional_edges` 实现动态路由——答得好深入，答得差换话题。
> 这用普通 API 调用需要自己维护状态机，等于重新造轮子。

### Q3: 数据量大了之后有什么性能瓶颈？

> **当前 V1 的瓶颈：**
> 1. localStorage 5MB 上限 — 面试次数多了可能不够用
> 2. ChromaDB in-memory — 重启后需要重新加载知识库
> 3. 所有 API 调用都走 DeepSeek — 延迟 1-3 秒，高并发扛不住
>
> **V4 的优化方向：**
> 1. 替换为 PostgreSQL（关系数据）+ Redis（缓存）
> 2. ChromaDB 持久化模式
> 3. 加入 Prompt 缓存和对话摘要，减少 Token 消耗

### Q4: 这个架构如果让你重来，哪里会改？

> 如果重来，我会在第一天把 **Agent 抽象层**设计好。
> 目前 ResumeAnalyzer、Interviewer、Scorer 三个 Agent
> 有大量重复代码（DeepSeek 调用、JSON 解析、错误处理），
> 可以提取一个 `BaseAgent` 抽象类，子类只需要实现 prompt 和 output schema。
>
> 但这个是"v2 重构项"，不影响当前功能。
