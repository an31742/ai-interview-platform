### Day51 — Token 机制 + 数据库设计

**🎯 学习目标：** 理解 Token 的计算方式和成本模型

```
上午 · AI 学习 (2h)
────────────────────────────────────────────────────────────────
📖 原理：
   Token 是大模型的最小计价单位，不是按字符算的。
   1 个中文 ≈ 1-2 Token，1 个英文单词 ≈ 1 Token
   DeepSeek: ¥1/1M 输入Token, ¥2/1M 输出Token

🔑 核心概念：
   · Tokenization — 文本 → Token 序列的切分方式
   · Context Window — 模型能"看到"的最大 Token 数（DeepSeek: 128K）
   · 成本计算 — 一次面试对话 ≈ 2000 Token 输入 + 500 Token 输出
   · Token 优化 — 减少冗余上下文、对话摘要压缩

📝 面试考点：
   · "1个中文大概等于几个 Token？"
   · "128K Context Window 能装多少内容？"
   · "怎么控制 API 调用的成本？"

💡 项目关联：
   一次模拟面试的 Token 消耗：
   · System Prompt: ~500 Token（含简历+JD）
   · 用户回答: ~200 Token/轮
   · AI 提问: ~300 Token/轮
   · 10轮对话 ≈ 5000 Token 输入 + 3000 Token 输出
   · 成本: 5000×¥1/1M + 3000×¥2/1M ≈ ¥0.011/次面试

下午 · 项目实践 (3h)
────────────────────────────────────────────────────────────────
🛠️ 任务：数据库设计 + 项目初始化
   1. 设计 Zustand Store 结构（ Resume / Session / Review / ErrorBook ）
   2. 创建 Next.js 项目骨架
   3. 搭建基础路由（ /interview 及其子页面 ）

📄 产出：

### Day52 — Embedding + 项目初始化

**🎯 学习目标：** 理解 Embedding 原理，完成项目基础架构

```
上午 · AI 学习 (2h)
────────────────────────────────────────────────────────────────
📖 原理：
   Embedding = 把文本变成"向量"（一串数字），
   语义相似的文本在向量空间中距离更近。
   "Vue响应式" 和 "Proxy依赖收集" 的向量距离 < "Vue响应式" 和 "盒模型"

🔑 核心概念：
   · 向量维度 — DeepSeek Embedding 输出 1024/2048 维向量
   · 余弦相似度 — 衡量两个向量方向的相似程度（-1 到 1）
   · 向量数据库 — 专门存储和检索向量的数据库（ChromaDB）
   · Embedding 模型 vs 对话模型 — 用途不同，不能混用

📝 面试考点：
   · "Embedding 是什么？怎么计算相似度？"
   · "为什么用向量数据库而不是 MySQL 存文本？"
   · "Embedding 模型和对话模型有什么区别？"

💡 项目关联：

### Day53 — RAG 原理 + 登录注册

**🎯 学习目标：** 理解 RAG 四步流程，实现用户系统

```
上午 · AI 学习 (2h)
────────────────────────────────────────────────────────────────
📖 原理：
   RAG = Retrieve-Augmented-Generation（检索增强生成）
   核心思想：让模型在回答前，先从知识库检索相关信息。

🔑 RAG 四步流程：
   ① 文档分段 — PDF/文本切分成小段（500-1000字符/段）
   ② 向量入库 — 每段生成 Embedding，存入 ChromaDB
   ③ 检索召回 — 用户提问 → 向量化 → 余弦相似度 TOP-K 召回
   ④ 增强生成 — 原始问题 + 检索结果拼在一起 → 给大模型生成回答

📝 面试考点：
   · "RAG 和微调有什么区别？"
   · "为什么 RAG 比微调更适合知识库场景？"
   · "RAG 的检索策略有哪些（稀疏/稠密/混合）？"

💡 项目关联：
   简历 RAG：上传简历→分段→Embedding→Chromadb→面试时检索→增强AI追问

下午 · 项目实践 (3h)
────────────────────────────────────────────────────────────────
🛠️ 任务：简历 RAG 知识库（V2 准备）

**🎯 学习目标：** 理解 Function Calling 机制

```
上午 · AI 学习 (2h)
────────────────────────────────────────────────────────────────
📖 原理：
   Function Calling ≠ 大模型"调用"函数。
   是模型输出一个结构化的"调用请求"，由开发者真正执行。

🔑 核心概念：

   · Tool Result — 开发者执行后返回结果给模型
   · Parallel Tool Calls — 模型一次调用多个工具

## 🎯 面试官问你"你怎么学的 AI"时的回答

> **不要只说"掘金和GPT"**（这是你字节面试的致命扣分项）。

**正确的回答（三层学习法）：**
> 我学 AI 应用开发是分三层系统学的：
>
> **第一层：理论 + 官方文档（广度）**
> 我按 LangChain 和 LangGraph 的官方教程系统过了一遍，
> 理解了 ChatModel、PromptTemplate、Chain、Agent 等核心概念。
>
> **第二层：手写 Demo + 源码阅读（深度）**
> 在 AI 面试训练平台中，我从手写 DeepSeek API 调用开始，
> 逐步替换为 LangChain 的封装，最后用 LangGraph 实现状态图。
> 每个环节都自己写过一遍，不是只调包。
>
> **第三层：博客输出 + 项目实践（输出）**
> 我把学到的东西写成技术博客发在掘金，
> 项目的每步设计都同步输出文档（架构图/数据流/技术选型），
> 面试官你现在看到的这些文档就是我的学习产出。
>
> **总结：理论→实践→输出，三层循环。**
