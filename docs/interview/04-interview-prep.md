> **目标：** 面试官问到这个项目时，你能自信地说清架构设计、技术选型、难点和亮点。
> 本文档涵盖：项目介绍话术、技术选型问答、难点故事、PREP 答题模板。

## 一、项目介绍篇

### 1.1 一句话介绍

> **"这是一个基于 Next.js + DeepSeek 的 AI 智能面试训练平台。
> 用户上传简历后，AI 自动分析技术短板，然后进行多轮模拟面试，
> 结束后生成评分报告和错题本，形成面试准备的完整闭环。"**

### 1.2 项目介绍（PREP 结构、30秒版）

| 步骤 | 内容 |
|------|------|
| **P**oint | 我独立开发了一个 AI 面试训练平台，目的是解决求职者面试准备效率低的问题 |
| **R**eason | 市面上没有免费的、针对个人简历定制化出题的面试工具，都是通用题库 |
| **E**xample | 用户上传简历后，AI 自动提取技术栈 → 生成针对性面试题 → 模拟面试 → 评分 → 错题追踪 |
| **P**oint | 所以这个项目的核心价值是：**让每一道面试题都跟你的简历有关，不做无用功** |

### 1.3 项目介绍（1分钟完整版、面试用）

> **🎤 面试逐字稿：**
>
> "这个项目叫 AI 智能面试训练平台，是我为**简历核心项目**开发的。
>
> 它的核心流程是：用户上传 PDF 简历 → 通过 pdf-parse 解析文本 →
> 调用 DeepSeek 提取结构化信息（技术栈、项目经历、工作年限）→
> AI 分析出技术短板 → 然后进入模拟面试环节。
>
> 模拟面试是最核心的部分：我用了 **LangGraph 的状态图**来管理面试流程，
> AI 面试官会根据用户的回答动态决定追问还是切换话题。
> 面试结束后，Scorer Agent 从五个维度评分（基础能力、项目深度、系统设计、
> 表达沟通、AI能力），生成详细的面试报告。
>
> 另外还有一个**复盘导入**功能：把真实面试的录音转写或记录导入，
> AI 自动提取错题到错题本，追踪掌握度。
>
> 技术栈是 Next.js 16 + React 19 + TypeScript，AI 部分用了 LangChain +
> LangGraph，状态管理用 Zustand，RAG 向量库用 ChromaDB。
> 当前是 V1 版本，数据存在 localStorage，后续计划接入 PostgreSQL 和 Redis。"

## 二、技术选型问答篇

### Q1: 为什么用 Next.js 而不是纯 React SPA？

```
┌──────────────────────────────────────────────────────────────────┐
│  SPA (Create React App)         vs     Next.js App Router        │
├──────────────────────────────────────────────────────────────────┤
│  需要独立后端 (Express)               一体化的前后端               │
│  手动管理路由                         文件即路由                   │
│  API 需要独立部署                     API Routes 同项目部署        │
│  SSR 需要额外配置                      原生支持 SSR/SSG           │
│  Streaming 需要手写                    SSE 流式输出原生友好        │
│  部署到 Vercel 需要适配                一键部署 Vercel            │
└──────────────────────────────────────────────────────────────────┘
```

**面试回答：**
> "选 Next.js 是因为这个项目需要同时管理**前端页面**和**AI API 路由**。
> Next.js 的 App Router 让我可以把页面路由（/interview/mock）和
> API 路由（/api/interview/chat）放在同一个项目里，部署也只需要一个平台。
> 而且面试对话中的 SSE 流式输出，Next.js 的 Streaming 支持得很好。"
>
> **如果面试官追问：** "那你用了哪些 Next.js 特性？"
> - 文件即路由 → interview/ 下的目录结构就是路由
> - Server Component → 静态页面用 SSR（仪表盘）
> - Client Component → 交互页面用 'use client'（面试对话）
> - Route Handler → POST /api/interview/chat 处理 SSE 流

### Q2: 为什么用 DeepSeek 而不是其他大模型？

| 模型 | 价格 (1M Token) | 中文能力 | 推理速度 |
|------|----------------|---------|---------|
| DeepSeek | ¥1 (输入) / ¥2 (输出) | ✅✅ 最强中文模型之一 | 快 |
| GPT-4o | $2.5 (输入) / $10 (输出) | ✅ 好 | 快 |
| Claude Sonnet | $3 (输入) / $15 (输出) | ✅ 好 | 快 |

**面试回答：**
> "三个原因：
> 1. **成本** — DeepSeek 的价格是 GPT-4o 的 1/10 左右，个人项目成本可控
> 2. **中文能力** — 面试场景需要中文问答，DeepSeek 在中文理解上不输 GPT-4
> 3. **兼容 OpenAI SDK** — DeepSeek 兼容 OpenAI 的 API 格式，迁移成本极低
>    将来想换 Claude 或 GPT，只需要改 baseUrl 和 apiKey"

### Q3: 为什么用 Zustand 而不是 Redux/Context？

```typescript
// Zustand 优势：精确订阅，不浪费渲染
// ✅ 只有 streamingContent 变化时才重渲染
const content = useInterviewStore(s => s.streamingContent)

// ❌ Context: 任何状态变化都重渲染整个子树
// ❌ Redux: 样板代码太多，不适合中小型项目
```

**面试回答：**
> "这个项目的状态管理有三类：
> 1. **持久化数据**（简历/会话/错题本）→ Zustand + persist 自动存 localStorage
> 2. **运行时状态**（流式内容/加载态）→ Zustand 零 Provider，直接订阅
> 3. **UI 状态**（选中的tab/弹窗）→ React useState
>
> 选 Zustand 而不是 Redux 是因为项目规模不需要 action/reducer 的繁琐结构。
> 选 Zustand 而不是 Context 是因为面试对话中 streamingContent 每秒更新多次，
> Context 会导致整个组件树重渲染，Zustand 的精确保留了性能。"

### Q4: 为什么用 LangGraph？

**面试回答：**
> "模拟面试不像普通聊天——AI 需要根据用户的回答**动态决定下一步**。
> 比如用户 Vue 响应式答得好 → 继续深挖依赖收集；
> 答得差 → 切换到 CSS 话题，不浪费时间。
>
> LangGraph 的 StateGraph 提供了**条件路由**机制，我能定义：
> - Node（阶段）：自我介绍 → 项目深挖 → 基础考察 → ...
> - Edge（条件）：评分 < 4 分 → 切换阶段；评分 >= 7 分 → 继续追问
>
> 没有 LangGraph，我需要手写一个状态机，代码会变得很复杂。"

### Q5: 这个项目你觉得哪里做得最好？

> **"我觉得最好的设计是 SSE 流式协议。**
> 面试对话中 AI 的回答需要逐字显示（打字机效果），
> 但用户回答是一次性提交的，不需要流式。
> 所以前端 → 后端用普通 POST，后端 → 前端用 SSE Stream。
> 这个设计比 WebSocket 轻量，比轮询实时，而且 SSE 原生支持断线重连。"

### Q6: 如果让你重来，哪里会改？

> **"我会在 V1 阶段就做好数据库设计。**
> 当前用 localStorage 持久化，单用户没问题，
> 但如果要做成多用户产品，数据迁移会比较痛苦。
> 应该在项目初始化时就设计好 PostgreSQL 的表结构，
> Zustand 只是前端的缓存层，而不是持久化层。
>
> 另一个是 **Agent 抽象**。目前三个 Agent 有很多重复代码，
> 可以提取一个 BaseAgent 类，统一管理 Prompt 构建、模型调用、JSON 解析。
> 这是 V2 的优化方向。"

## 三、项目难点故事篇

> **面试必问题：** "你在项目中遇到的最大挑战是什么？"
> **千万不要说"没有挑战"**（这是你字节面试的致命错误）。
> **准备 3 个 STAR 故事，每个 1 分钟。**

### 故事 1：SSE 流式渲染的性能优化

```
S (背景)
└─ 模拟面试需要 AI 逐字输出，但持续 SSE 推送会导致频繁 DOM 更新

T (任务)
└─ 保证 60fps 流畅渲染，不卡顿不闪烁

A (行动)
└─ 我做了三个优化：
   1. requestAnimationFrame 合并渲染周期，不每收到一个 chunk 就更新 DOM
   2. 增量 DOM diff：只更新变化的部分，不重新渲染整个消息列表
   3. ScrollAnchor：AI 输出时自动滚动到底部，但用户手动滚动查看历史时不强制

R (结果)
└─ 实现了流畅的打字机效果，即使在低端设备上也不卡顿
```

**加分技巧：** 说到 "requestAnimationFrame" 时，面试官会眼前一亮。
这是很多前端不知道的优化手段。

### 故事 2：LangGraph 状态图的条件路由

```
S (背景)
└─ 初期模拟面试是线性的：固定顺序问完所有题，不管用户答得怎么样

T (任务)
└─ 需要让 AI 面试官像真人一样，根据回答动态调整

A (行动)
└─ 我引入了 LangGraph 的 StateGraph：
   - 定义了 5 个 Node（阶段）：自我介绍 → 项目深挖 → 基础 → 系统设计 → QA
   - 每个 Node 输出评分后，通过 conditional_edges 判断路由
   - 评分 >= 7 → 继续追问同一话题
   - 评分 < 4 → 切换下一阶段
   - 评分 4-6 → 换个角度问

R (结果)
└─ 面试体验大幅提升，不再是固定流水线，而是有"智商"的面试官
```

### 故事 3：ChromaDB 向量检索的上下文增强

```
S (背景)
└─ AI 面试官在面试过程中会"失忆"——记不住简历的细节

T (任务)
└─ 让 AI 在追问时能精确引用简历中的项目经历

A (行动)
└─ 我实现了 RAG 流程：
   1. 简历 PDF 解析后，用 TextSplitter 分段
   2. 每段生成 Embedding 向量存入 ChromaDB
   3. 面试时从对话历史提取关键词，检索最相关的简历段落
   4. 将检索结果拼入 System Prompt

R (结果)
└─ AI 能说出"你在联想做的 Legion Zone 项目中，流式渲染是怎么实现的？"
   而不是笼统地问"介绍你的项目"
```

## 四、PREP 答题模板（面试通用）

> **你的 13 场面试复盘显示：回答没结构是最致命的扣分项之一。**
> **下面是标准化答题模板，每个问题都用这个结构练习。**

### PREP 标准框架

```
┌─────────────────────────────────────────────────────────────┐
│  P (Point)   → 一句话结论（10% 的时间）                       │
│                例："我用 Zustand 管理状态，主要原因是精确订阅"   │
├─────────────────────────────────────────────────────────────┤
│  R (Reason)  → 为什么这么做（30% 的时间）                     │
│                例："Context 在流式场景会导致不必要的重渲染..."   │
├─────────────────────────────────────────────────────────────┤
│  E (Example) → 项目里的实际例子（50% 的时间）                  │
│                例："在面试对话中，streamingContent 每秒更新..." │
├─────────────────────────────────────────────────────────────┤
│  P (Point)   → 总结（10% 的时间）                             │
│                例："所以选择 Zustand 是因为它的精细粒度控制..." │
└─────────────────────────────────────────────────────────────┘
```

### 实操模板：随便抽一个技术问题练习

> **题目：** "为什么选这个技术方案？"
>
> **P** — "我选了 X，主要原因是 Y 和 Z。"
> **R** — "因为项目需要 A 和 B，而 X 在这两方面比竞品好。"
> **E** — "比如在 xxx 场景中，我们遇到了 C 问题，用 X 之后 D 得到了改善。"
> **P** — "所以在综合考虑后，X 是当时最合理的选择。"

## 五、面试铁律（来自你13场复盘）

### 绝不能说 ❌

| 原话 | 为什么致命 | 改成 |
|------|-----------|------|
| "没有挑战" | 面试官认为你项目没深度 | 准备3个STAR故事 |
| "我看别人的逻辑" | 7年经验还在看别人代码？ | "虽然不是我最初写的，但我通过XX深入理解了原理" |
| "难点不多" | 面试官觉得你技术天花板低 | 说2-3个具体技术挑战 |
| "在学习"（空洞） | 面试官感受不到你的能力 | "我最近做了XXX，在项目里实现了XXX" |
| "薪资高才转行" | 动机太单一 | "薪资是契机，坚持7年因为解决问题的成就感" |
| "掘金和GPT" | 碎片化学习，没有体系 | "三层学习法：广度（文档）+ 深度（源码）+ 输出（博客）" |

### 必须做到 ✅

| 行为 | 原因 |
|------|------|
| 回答前**停顿2秒** | 想 PREP 结构，避免上来就啰嗦 |
| 先说结论再展开 | 面试官没耐心听你绕，先给结论显得思路清晰 |
| 每个项目带**STAR + 量化数据** | 证明是你做的，不是背的 |
| 说技术方案要提**trade-off** | 展现架构思维，不是只会用 |
